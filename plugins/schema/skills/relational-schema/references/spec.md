# Relational schema conventions, normative text

Version 1.2.

MUST / SHOULD / MAY carry their usual weight. A rule is a MUST only where following it costs
nothing and breaking it costs something later — naming, types, widths, migration discipline.
Where reasonable projects genuinely differ — how they isolate tenants, how they delete, how they
represent money in code — the rule is a SHOULD and the choice is the project's, recorded in its
own configuration rather than settled here. Rules marked **[pg]** need PostgreSQL or an engine
with the same feature; the rest are engine-neutral. Rules marked **[app]** cannot be expressed in
DDL and need the application to cooperate.

## K — Identifiers

**K1.** Every primary key MUST be a UUID v7 stored in the engine's native UUID type. Never
auto-increment, never v4, never ULID, never a string column holding a UUID.

**K2. [app]** The value MUST be generated by the application before insert, with a database
default as a backstop only.

**K3.** Every foreign key MUST end `_id`.

**K4.** Default shape: `<singular referenced table>_id`.

**K5.** Role shape: any other `<role>_id`, valid only if listed in the project's configuration.

**K6.** Where a project keeps a role allowlist, it SHOULD be checked in both directions: an
unlisted shape fails, and a listed key that nothing uses fails too, so the list cannot rot into
stale documentation.

### Why v7 rather than v4

A v7 sorts by creation time, so it doubles as a tiebreak (U4), keeps index inserts local instead
of scattering them across the B-tree, and stays opaque to the client. Generating it in the
application means the ID exists before the row does, which is what lets a client dedupe a retry
and a caller build a graph of related rows in one round trip.

### Why exactly two foreign key shapes

A role key earns its place when the role matters more than the target (`owner_id`), when one
table references another twice (`from_stage_id` / `to_stage_id`), or when the column names *who
did something*. That last case is why the shape exists: an actor column cannot be `user_id` when
a table carries three of them, so it is named for the act — `creator_id`, `approver_id`,
`completer_id`. The allowlist is what stops "any noun plus `_id`" becoming a third shape by
drift, and K6's second direction is what stops the allowlist becoming stale documentation.

## T — Multi-tenancy

Skip this section entirely if the system is single-tenant. If it applies, it applies to every
table holding tenant data.

**T1.** One tenant column, one name, declared in the project configuration and used everywhere.
It SHOULD take the domain's own word rather than `tenant_id` if the domain has one, and that word
SHOULD then be used in code, columns, routes and tests alike.

**T2.** Every tenant-scoped table MUST carry that column, non-null, with a foreign key to the
tenant table.

**T3. [pg]** Where isolation is enforced in the database, row-level security SHOULD be enabled
**and forced** on every such table, in the same migration statement block that creates it. Forced,
or the table owner is exempt and the boundary is decorative.

**T4. [app]** The tenant identity MUST reach the session through a connection-scoped variable,
set around the reads that need it and never for the lifetime of a request.

**T5. [app]** Isolation SHOULD be enforced by the database rather than by an application-layer
query scope. Where it is a scope, it MUST pass through one choke point no query can bypass — a
repository layer or a connection wrapper, not a convention — because a scope that any query can
forget is not a boundary.

**T6.** Every tenant-scoped parent MUST carry `UNIQUE (tenant_column, id)`, and every child
foreign key MUST be re-declared as a composite `(tenant_column, child_id) → parent (tenant_column,
id)`.

**T7.** Every index on a tenant-scoped table MUST lead with the tenant column.

### Why T6 is worth the extra constraint

Single-column foreign keys let a row in tenant A point at a parent in tenant B. Row-level security
normally prevents that, but RLS is a runtime policy and this is a structural impossibility — it
survives a disabled policy, a superuser connection, a compromised application and a bad backfill.
It is the difference between cross-tenant corruption being unlikely and being unrepresentable.

### Where T3 is unavailable

Engines without row-level security cannot satisfy it. T6 then stops being belt-and-braces and
becomes the only structural defence, and isolation additionally needs a single choke point in the
application that no query bypasses — a repository layer or a connection wrapper, not a convention.
Report this as unmet rather than not applicable: the risk did not go away because the feature did.

## C — Column types

**C1.** Bounded strings MUST use a length-limited type at a power of two: 8, 16, 32, 64, 128,
256, 512, 1024, 2048.

**C2.** A non-power-of-two width is permitted only where an external standard or format fixes it.
Each such column MUST appear in the project configuration with the standard named.

**C3.** Unbounded text MUST use the engine's unbounded type, and only for genuinely unbounded
content: prose bodies, notes, message content, prompt text, document chunks.

**C4.** A column holding a value from a closed set MUST be a length-limited string wide enough for
its longest member. Engine-native enum types MUST NOT be used, and neither MUST a check constraint
listing the members.

**C5.** Semi-structured data MUST use a binary JSON type, never a text JSON type.

**C6.** Semi-structured columns are for sparse, schema-varying or third-party-shaped data.
Anything filtered or aggregated on regularly MUST be a real column.

**C7. [app]** Every semi-structured column MUST have a typed representation in the application.

**C8.** Where a project keeps a list of agreed semi-structured columns, adding one outside it
SHOULD carry its justification in the migration's name.

### Why powers of two

The widths carry no storage meaning in most engines. The point is that a reviewer never argues
about 50 versus 60, and a column that needs 300 is visibly a column somebody guessed at. It turns
a per-column debate into a lookup.

### Why not engine-native enums

Adding a value to a PostgreSQL enum type cannot run inside a transaction alongside other DDL on
older versions, removing one is unsupported, and the type is invisible to every tool that reads
the schema as strings. A check constraint has the same rigidity with worse ergonomics. The closed
set belongs in the application, where adding a member is a code change and a test; the column's
only job is to be wide enough for the longest member, which fails on the first insert that uses
the rarest branch if it is not.

### Why C2 requires naming the standard

`varchar(7)` is inexplicable. `varchar(7)`, listed as `period_month`, ISO `YYYY-MM`, is obvious.
Without the entry the next person rounds it to 8 and the format check quietly stops meaning
anything.

## D — Dates and times

**D1.** Every instant MUST be stored in a timezone-aware timestamp type, in UTC.

**D2.** A column suffixed `_at` MUST be an instant. A column suffixed `_on` MUST be a calendar
date. Both suffixes are reserved: nothing else may use them, and neither may be any other type.

**D3.** Range boundaries MAY be freely named (`period_start`, `effective_from`, `valid_until`) but
both ends of one range MUST share a type.

**D4.** Presentation timezone and week-start MUST be declared once in the project configuration
and applied at the edges only.

### Why reserve the suffixes

It makes the type readable without opening the schema, and it stops date arithmetic being run
against an instant — an error that does not raise. It just comes out wrong by the UTC offset,
which stays invisible until somebody in another timezone reads the report.

## M — Money

**M1.** Monetary amounts MUST be stored as an integer in the currency's minor unit, in a column
suffixed `_minor`. Never float, never decimal.

**M2.** The currency code MUST live in its own adjacent column on the same row, as ISO 4217.

**M3.** A currency MUST NOT appear in a column name.

**M4.** Every amount column MUST carry bounds as a check constraint, added unvalidated where the
engine supports it so the migration does not rewrite the table.

**M5. [app]** Amounts SHOULD be read and written through a typed value object carrying the
currency rather than as a bare integer. How that is expressed is the language's business.

**M6.** Amounts on a settled financial record MUST be immutable once written, enforced by a
trigger comparing old and new. Corrections are new rows, never edits.

### Why not decimal

Fixed-point decimal is arithmetically correct and still operationally wrong: it invites division,
its precision varies across drivers and ORMs, and it lets an amount exist without a currency
beside it. An integer plus a currency column plus a value object makes "9" unable to mean nine
cents in one place and nine dollars in another.

### Why M3

`price_usd` is a column you rename the day a second currency appears, along with every query that
names it. `price_minor` plus `currency` never needs renaming.

## L — Deletion and immutability

How a table handles deletion is a design choice, not a convention, and it is the project's to
make. Nothing here mandates a shape. What this section does is name the shapes that exist, say
what each one costs, and set out what MUST hold *once a shape is chosen* — because the common
failure is not picking the wrong one, it is picking one and implementing half of it.

**L1.** A table's deletion behaviour SHOULD be decided when the table is created rather than
discovered when the first delete is written.

**L2.** A table MUST NOT use more than one of these shapes at once. Two ways to be deleted is how
a row ends up visible to one query and absent from another.

| Shape | Fits | Costs |
|---|---|---|
| **Hard delete** | rows that are cheap to recreate, or that a retention policy exists to remove | nothing; this is the default and needs no ceremony |
| **Soft delete** | rows carrying authored content, or that history points at by id | every read must filter, and U1 applies |
| **Withdraw** (a status or an `archived_at`) | rows that stop being *offered* without stopping being *referenced* | a second state for every query that lists choices |
| **Append-only** | audit trails, state transitions, ledgers, usage counters | corrections become new rows, and readers must fold them |

**L3.** Where a table soft-deletes, the marker MUST be a nullable timestamp — `deleted_at` unless
the project's configuration names another — never a boolean, which cannot say when.

**L4.** Where a table soft-deletes, every read path MUST exclude deleted rows by default, and
U1 applies to its unique indexes.

**L5. [pg]** Where a table is append-only, UPDATE and DELETE MUST be rejected by a trigger, not by
application convention alone. An application guard is bypassed by a console, a migration, a
backfill script or a second service.

**L6.** A project MAY record its choice per table in the configuration. Doing so is what lets a
checker verify L3 and L4; leaving it out means those rules are simply not checked, which is a
legitimate choice and not a finding.

### Why a soft delete is not the safe default

It is the option that looks free and is not. Every query acquires a filter that is invisible when
forgotten, uniqueness stops working the obvious way, and the row that was "kept for safety" is
usually never read again. Reach for it when a delete destroys something a person wrote, or when
history references the row by id and the reference would otherwise be rewritten — not as a
reflex, and not because deleting feels frightening.

### Why L5 needs a trigger rather than a convention

Append-only tables are what metrics, invoices and disputed-access claims are computed from. A
table four codepaths can edit is a table nobody can defend.

## U — Uniqueness and ordering

**U1. [pg]** On a table that soft-deletes, every unique index MUST be partial:
`WHERE deleted_at IS NULL`. Exceptions — keys that must survive deletion, such as an address that
may not be reused by a second person — SHOULD be recorded with their reason.

**U2. [app]** Uniqueness conflicts MUST be detected from the database's own constraint violation,
never by a pre-flight `SELECT`, which is a race.

**U3. [app][pg]** That violation MUST be handled outside the aborted transaction. A failed
statement poisons the whole transaction, including the follow-up query that would turn the
violation into a message naming the holder.

**U4. [app]** Wherever "the newest row" is selected, ordering MUST include the primary key as a
tiebreak, not the timestamp alone.

**U5. [app]** Cursor pagination MUST order on a tuple ending in the primary key, and MUST handle
nulls in every sort column it offers.

### Why U4 matters more than it looks

Many drivers and ORMs serialise timestamps to whole seconds. Two rows written in the same second
then tie, and an arbitrary tiebreak means "the latest consent record" returns yes about half the
time. A v7 primary key (K1) sorts in creation order, so it resolves the tie correctly and free.

### Where U1 and T6 collide, and which wins

The composite tenant key T6 asks for — `UNIQUE (tenant_column, id)` on a parent — must stay
**total**, not partial. A foreign key can reference a unique constraint but not a partial index,
so making it partial to satisfy U1 would make T6 unimplementable. T6 wins: it is a structural
guarantee, where U1 protects a key from being held by a deleted row, and the key in question is
a surrogate nobody reuses. A conformance checker MUST exempt this one constraint from U1 rather
than reporting a conflict it cannot resolve.

### A trap worth stating

A partial unique index on a child table cannot see whether its *parent* is soft-deleted. Deleting
the parent must therefore explicitly release the child's key, and restoring the parent must
reclaim it — an operation that can fail, and should, rather than silently restoring a row whose
key somebody else has since taken.

## G — Migration discipline

**G1.** A migration MUST create its tables, indexes, constraints and security policies together,
in one unit. A table MUST NOT be able to exist anywhere without its policy.

**G2.** Ordering within a migration follows dependency order; references across migrations point
only backwards.

**G3.** Constraints that span the whole schema — composite tenant keys, foreign-key indexes,
full-text and trigram indexes, bounds, immutability triggers — belong in one final migration, each
driven from a declared list rather than written out per table.

**G4.** A migration MUST be self-contained. It MUST NOT read a table list, column list or SQL
fragment from application code that continues to evolve.

**G5.** Once a migration has run in any environment that is not disposable, it is finished. It
MUST NOT be edited, and later work MUST NOT be folded back into it.

**G6.** Every migration MUST be reversible, and the reversal MUST leave nothing behind.

**G7.** Foreign-key columns MUST be indexed. A composite index leading with the column counts;
anything covered by neither gets its own.

### Why G4 is the one people get wrong

A migration that imports a constant from application code describes whatever that constant becomes
later, not what it described when it ran. Production keeps the old shape, a fresh database is
built to the new one, and the two diverge silently. The failure surfaces months later as "works on
my machine" with no diff to point at.

### Why G5 forbids consolidation

Squashing history into a clean baseline is safe only while every deployment can be rebuilt from
scratch. Once a database holds data you cannot recreate, the migrations that built it are the only
description of how it got there, and a tidier file producing the same end state by a different
route will not apply to it.

### Why G7

PostgreSQL does not create an index for a foreign key. MySQL does. A team moving between them
loses the index without noticing, and finds out when a cascading delete or a join on a large child
table falls over.

## Project configuration

A project declares its own choices in `schema-conventions.toml` at the repository root. Keeping
the rules here and the choices there is what lets one copy of this standard serve several
codebases without forking per project. Every section below is optional: an absent section means
the rules that read it are not checked, not that the project has failed them.

```toml
[project]
engine = "postgres"            # postgres | mysql | sqlite | other
display_timezone = "UTC"       # D4
week_starts = "monday"         # D4

[tenancy]
enabled = true                 # false skips section T entirely
column = "workspace_id"        # T1
table = "workspaces"

# K5. Foreign keys whose name is a role rather than the table they point at.
# K6 fails an entry nothing uses, so this list cannot rot.
[keys.roles]
owner_id = "users"
assignee_id = "users"
creator_id = "users"
approver_id = "users"
from_stage_id = "pipeline_stages"
to_stage_id = "pipeline_stages"

# C2. Widths that are not powers of two, each with the standard that fixes it.
[columns.widths]
country = { width = 2, standard = "ISO 3166-1 alpha-2" }
currency = { width = 3, standard = "ISO 4217" }
period_month = { width = 7, standard = "YYYY-MM" }
access_token = { width = 2048, standard = "provider-sized OAuth token" }

# C8. Semi-structured columns that have been agreed.
[columns.json]
allowed = ["metadata", "payload", "custom_fields", "permissions"]

# L6. Optional. Naming a table here is what lets L3 and L4 be checked; omit the section and
# deletion behaviour is simply not checked, which is a legitimate choice. Tables not listed are
# not findings.
[lifecycle]
soft_delete = ["accounts", "contacts"]
append_only = ["audit_logs", "stage_transitions"]

# U1. Unique indexes that must survive a soft delete, each with its reason.
[uniqueness.exceptions]
users_email_unique = "an address may not be reused by a second person after deletion"
```

## Implementation notes by stack

The rules are identical; only the mechanism differs.

| | UUID v7 primary key | Soft delete | Money value object | Closed sets | Immutability |
|---|---|---|---|---|---|
| **Prisma** | `String @id @db.Uuid`, generated in app code | `deletedAt` plus a client extension | branded type or wrapper | TS union mapped to `@db.VarChar(n)` | DB trigger |
| **SQLAlchemy / Alembic** | `UUID(as_uuid=True)`, default `uuid6.uuid7()` | `deleted_at` plus a query mixin | `TypeDecorator` | `Enum(..., native_enum=False)` | DB trigger |
| **Eloquent / Laravel** | `HasUuids`, `uuid` column | `SoftDeletes` trait | custom cast | backed enum cast | DB trigger plus model guard |
| **Ecto** | `:binary_id`, app-generated | `deleted_at` plus a named query | embedded schema | `Ecto.Enum` on `:string` | DB trigger |
| **Drizzle** | `uuid()`, app-generated | `deletedAt` plus a filter helper | branded type | TS union on `varchar` | DB trigger |
| **dbmate / Flyway / raw SQL** | `uuid` column, app supplies it | `deleted_at` column | discipline at the call site | `varchar(n)` | trigger, written out |

Two traps when porting:

- **Prisma's `@default(uuid())` is v4.** It satisfies "a UUID" and violates K1 for every reason K1
  exists. Generate v7 in application code and pass it in.
- **ORMs that hide soft deletes globally** make the soft delete easy and append-only harder to
  notice: a global filter gives no hint that a table should reject writes outright. The trigger is
  what makes append-only true, in every stack on this list.
