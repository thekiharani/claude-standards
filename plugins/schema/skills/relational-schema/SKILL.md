# Relational schema conventions

A portable standard. Every rule is a property of the **resulting schema**, so any migration
tool satisfies it its own way. Rules carry stable IDs (`K1`, `T6`, `C4`) so a review comment,
a commit message or a failing check can cite one.

## Using this skill

**Designing or changing a schema.** Read `references/spec.md` for the rule that applies. It is
the normative text; this file is only the map. Cite the ID when you explain a choice, because
"varchar(64), rule C1" ends an argument that "varchar(64), feels right" starts.

**Reviewing a schema or a migration.** Run the checker rather than reading DDL by eye:

```bash
python scripts/verify_schema.py --url "$DATABASE_URL"
```

It queries the live catalogue, not the migration files, because the catalogue is what the
application actually runs on. Migration files describe intent; a database that drifted from them
is the thing that breaks. Output is one line per violation, keyed by rule ID. `--format json`
for CI, `--rules K,C` to check a subset, `--config` to point at a project's own settings.

**Adopting it in a project that already has a schema.** Run the checker first and read what it
says before changing anything. An existing schema will fail rules, and the useful question is
which failures are worth a migration and which are worth an entry in the config's exception
list. Both answers are legitimate; pretending the schema conforms when it does not is the only
wrong one.

## The rules, in one screen

Read `references/spec.md` for the normative text and the reasoning. This index exists so you can
tell whether a rule applies before loading it.

| ID | Rule |
|---|---|
| **K1-K2** | Primary keys are UUID v7 in the native UUID type, generated by the application before insert |
| **K3-K6** | Foreign keys end `_id` and take one of two shapes: `<singular table>_id`, or an allowlisted `<role>_id` |
| **T1-T7** | Multi-tenant: one tenant column, composite `(tenant, id)` keys, tenant-leading indexes, and a boundary the application cannot forget |
| **C1-C2** | Bounded strings at a power of two, unless an external standard fixes the width and the column names it |
| **C3** | Unbounded text only for genuinely unbounded content |
| **C4** | Closed sets are width-checked strings, never engine-native enum types |
| **C5-C8** | Binary JSON only, for sparse or third-party-shaped data, with a typed representation in the application |
| **D1-D4** | Instants are timezone-aware UTC; `_at` and `_on` suffixes are reserved and typed |
| **M1-M6** | Money is an integer minor unit plus an adjacent currency column, bounded, immutable once settled |
| **L1-L6** | Deletion is the project's choice; whichever shape it picks, it implements all of it |
| **U1-U5** | Partial unique indexes on soft-deleted tables; conflicts caught from the database; key in every sort |
| **G1-G7** | Migrations are self-contained, reversible, and frozen once they have run somewhere real |

## Two rules people get wrong, and why

These two cause damage that surfaces months later with no diff to point at, so raise them even
when nobody asked.

**G4, a migration reads nothing it does not carry.** A migration that imports a constant from
application code describes whatever that constant becomes later, not what it described when it
ran. Production keeps the old shape, a fresh database is built to the new one, and the two
diverge silently. Column lists, table lists and SQL fragments belong in the migration, frozen
with it.

**G5, a migration that has run is finished.** Squashing history into a tidy baseline is safe
only while every database can be rebuilt from scratch. Once one holds data you cannot recreate,
the migrations that built it are the only description of how it got there, and a cleaner file
reaching the same end state by a different route will not apply to it. When someone asks to
consolidate migrations, ask first whether any database has run them.

## Scope and honesty about it

Some rules need an engine feature. `references/spec.md` marks those `[pg]`. On MySQL, SQLite or
a cloud warehouse there is no row-level security, so T3 cannot be met and T6 stops being a
belt-and-braces measure and becomes the only structural defence - say so rather than reporting
a pass.

Some rules need application cooperation and no DDL can express them: K2 (who generates the
UUID), C7 (a typed representation), M5 (a money value object), U2-U3 (catching a conflict from
the database, outside the aborted transaction). The checker reports these as `unverifiable`
rather than passing them, because a green check that proves nothing is worse than no check.

## Adapting it to a project

A project declares its own specifics in `schema-conventions.toml` at the repository root:
the tenant column's name, the string widths it has agreed beyond the powers of two, its role-key
allowlist, how its tables delete. Every section is optional, and an absent one means those rules
go unchecked rather than unmet. `references/spec.md` has the format. Keep the *rules* here
and the *choices* there - that is what lets one copy of this serve several codebases without
drifting into a fork per project.
