# Near-zero comments

The default is **no comment**. A comment is an exception that has to earn its place, and most do
not. A name that needs a comment is the wrong name.

This binds every file in a project, not just source: Dockerfiles, `docker-compose.yml`, CI
workflows, Terraform, Kubernetes manifests, shell scripts, SQL, stylesheets, templates, and every
kind of config. There is no file type this relaxes for.

## The test

Delete the comment. Ask whether the next person changes the code for the worse.

If yes, keep it. If no - if they would simply read the code and understand it - it goes. That is
the whole decision procedure, and it is deliberately hard to pass.

Applied honestly, it removes most comments people write. That is the intended outcome, not an
overcorrection.

## Never a comment

**Restating the code beneath it.** `// loop over the users` above a loop over the users. This is
the most common failure by a wide margin, and it hides inside comments that look like prose. Watch
especially for a docblock whose first line names the class again: "The one-time code that signs
somebody in" above `class SignInCode` says nothing the declaration did not.

**A docblock on an obvious member.** `/** Get the name. */` above `getName()`. If the only content
is the identifier with more words, delete it.

**Generated or framework boilerplate.** Config banners, scaffold headers, `{{-- Body --}}`
placeholders, `# Generated by ...` blocks that no longer describe anything. These came from a
generator, not from the team. Delete them the first time the file is touched.

**Commented-out code.** Including a default left commented as a hint. Version control remembers it;
a commented block does not say whether it is a plan, a rollback or an accident.

**`TODO`, `FIXME`, `XXX`, `HACK`.** It is an issue or it does not exist. A TODO is a decision
deferred where nobody will see it.

**Section labels.** `// Handlers`, `// --- state ---`, `/* Queries */`. A file that needs
signposting is a file that needs splitting.

**A separator or a banner.** Rows of `=` or `-` are decoration.

## Always kept

**Type annotations the tooling needs.** `@param`, `@return`, `@var`, `@template`, generics hints,
`# type:` comments, `//go:generate`, `eslint-disable`, `@ts-expect-error`, pragmas. These are load
bearing, not prose. They are not comments in the sense this rule is about, and a linter or type
checker fails without them.

**The one or two lines of *why* behind a decision invisible in the code.** This is the only prose
that survives, and it is worth writing well. The cases that qualify look like:

- a constraint caught outside its transaction, because the failure aborts every statement after it
- a tiebreak on the key rather than the timestamp, because the format carries whole seconds
- a variable set around one read rather than a whole request, because the policies OR rather than
  intersect
- a swallowed exception, saying why swallowing is correct here
- a magic number whose source is a provider's documented limit
- an ordering dependency between two lines that looks arbitrary and is not

What these share: the code is correct, it looks wrong or arbitrary, and a reasonable person would
"fix" it. The comment exists to stop that.

## Shape

A class or module gets at most a short paragraph, three or four lines. Anything inline is one or
two. If the reasoning needs more, it is not a comment - it belongs in the commit message, which is
the right place for an argument, or in a document if it is a design rather than a decision.

The code says *what*. The commit body says *why it was worth doing*. The file carries only what
stops the next reader breaking it.

## Example and sample files

`.env.example`, `config.sample.yml` and their kind are the one place where explanation is the
point: they exist to be read by somebody who has never seen the system, and a bare list of keys
tells them nothing.

The licence is narrow:

- Explain what a setting is **for**, or what breaks when it is wrong. Never restate its name:
  `# The database host` above `DB_HOST` is noise.
- Two lines per setting, or per group of related settings. Group where you can - six variables
  configuring one provider want one comment, not six.
- Say what a value must differ on between environments, because that is the mistake these files
  exist to prevent.
- No values on anything naming a credential. An example names variables, never their values.

```bash
# Local on a laptop, object storage on a server: the web tier and the worker are separate
# containers there, and a file only one of them can see is an upload that never processes.
UPLOAD_DISK=local
```

That earns its place. `# The upload disk` does not.

## Auditing a codebase

Do not read every file to judge this. Run the auditor, which finds the mechanically detectable
failures and ranks the rest for reading:

```bash
python scripts/audit_comments.py path/to/repo
python scripts/audit_comments.py path/to/repo --format json   # for CI
python scripts/audit_comments.py path/to/repo --category restates
```

It reports TODO markers, commented-out code, section labels, generated boilerplate, docblock
openers that restate the declaration, comments whose words already appear in the line below, and
blocks past the shape limit. It does not judge whether a *why* is worth keeping - only a reader
can, and the auditor ranks files by prose density so the reading starts where it pays.

Measured on a codebase held to this rule, prose comments come to roughly 4% of a TypeScript front
end and 7% of a PHP back end. Take that as a thermometer rather than a target: a small file skews
high for no reason worth acting on, and density says nothing about whether the comments that
survive are the right ones. The per-file ranking is the useful half of that output.

## A note for whoever is writing the code

If you are a model writing code for this project, this rule is aimed at you more than at anyone
else. The tendency is to narrate: to explain a decision at the moment of making it, because the
reasoning is right there and feels worth capturing. It usually is worth capturing - in the commit
message.

Two specific habits to watch. Writing a summary sentence, then a blank line, then the real reason:
the summary is almost always the class name restated, and cutting it loses nothing. And writing
three paragraphs where the shape allows one, because each felt necessary while writing it. Draft
it, then read it again and cut, the way you would a paragraph of prose.
